# RA-622 spike: Prove case types and case workflows

## Problem Statement

The existing applications support re-accreditation. Before delivering in-year accreditation changes, the team needs evidence that another case type can use the existing case management framework, declare its own workflow, and return an outcome to the correct operator request.

The spike should answer those technical questions with the smallest connected implementation. It is a foundation for later feature delivery, rather than a complete Add ORS journey. The broader RA-622 research includes tonnage changes and ORS/interim-site additions; this implementation uses one prepared ORS addition as its representative example and documents the implications for the other changes.

## Solution

Run the four existing application services locally. Add a small section on the operator landing page linking to one explicitly configured granted accreditation. Its summary displays the existing approved sites and a Change link. Change opens one prepared proposed ORS for submission. Only this fixed accreditation supports the spike change entry; other granted accreditations do not gain a Change link.

The flow is:

1. The demonstrator opens the fixed granted accreditation from the new operator landing-page section, follows Change, and submits the prepared ORS proposal.
2. The operator backend persists a separate request and submits it through the real management ingestion API. At most one request can be active against the accreditation.
3. Management displays the new case type, its target, proposal, case reference and current state.
4. The caseworker starts assessment and approves or refuses the case. Alternatively, the operator withdraws a submitted request before assessment starts.
5. The terminal outcome is recorded in both services. Approval makes the proposed ORS visible alongside the fixed accreditation's baseline sites and earlier approved additions. Every confirmed terminal outcome restores Change and allows a new request with a new identity. Refusal and withdrawal add no site. The predefined ORS can be submitted and approved again through a new request, allowing repeated demonstrations without resetting data. The target accreditation remains Granted throughout.

The visible approval effect is reconstructed from unchanged ReEx baseline sites plus one approved proposal per completed approved request persisted in the operator database. Separate requests can contribute entries with identical predefined site details. Replaying a callback for the same request adds nothing extra. This proves the local accreditation read behaviour. An actual ReEx amendment remains a later feature requirement.

### Questions the spike must answer

- Can another type be ingested, persisted, listed and rendered alongside re-accreditation?
- Can that type declare a different workflow with alternative terminal outcomes whose actions are enforced by the existing engine?
- Can it implement its own outcome behaviour without depending on the re-accreditation module?
- Can management decisions and operator withdrawal cross the real service boundary and update only the correlated request/case?
- Can approval affect the fixed accreditation view while refusal and withdrawal leave its approved sites unchanged?
- Can one active request be enforced, and can each terminal request be retained while a new request is raised, including repeated approvals of the predefined ORS without resetting data?
- Do existing audit and template snapshots work for the new type, and which shared assumptions actually need changing?

### Completion boundary

The spike is complete when the connected approval, refusal and submitted-request withdrawal paths pass, including new requests after each outcome and approval of the same predefined ORS through two distinct requests without a reset, the focused technical checks below pass, and a short approach note records the findings and remaining delivery scope. Completion does not depend on building any deferred journey. Extra product behaviour requires a later ticket or an explicit change to this scope.

## User Stories

1. As a demonstrator, I want a new operator landing-page section linking to one fixed granted accreditation with a Change action, so that I can demonstrate the intended entry point without building a catalogue.
2. As a demonstrator, I want the request and accreditation identified separately, so that I can prove requesting a change does not reopen the accreditation.
3. As a caseworker, I want to find and open an Add ORS case, so that I can demonstrate type-specific presentation within existing case management.
4. As a caseworker, I want to start assessment and approve or refuse the case, so that I can demonstrate the new module's alternative outcomes.
5. As a demonstrator, I want to see the decision returned to the operator request, so that I can prove the outcome crosses the actual service boundary.
6. As a maintainer, I want invalid transitions and mismatched outcomes rejected, so that the demonstration establishes meaningful engine and correlation guarantees.
7. As a maintainer, I want persisted cases to retain their workflow version, so that later feature work can extend the module without silently changing existing cases.
8. As a delivery team member, I want the proven approach, limitations and remaining work recorded, so that the next ticket can build on this branch with a clear scope.
9. As a demonstrator, I want to submit a predefined ORS, so that I can exercise the change journey without entering site details or evidence.
10. As an operator, I want to withdraw a submitted request before assessment, so that I can prove an operator action closes its linked management case.
11. As an operator, I want only one active request and a new Change action after approval, refusal or withdrawal, so that completed attempts are retained without blocking another attempt.
12. As an operator, I want an approved ORS visible on the fixed accreditation summary and refused/withdrawn proposals excluded, so that the demo proves the effect of each outcome.
13. As a demonstrator, I want to approve the same predefined ORS in separate new requests, so that I can repeat the demonstration without resetting stored data.

## Implementation Decisions

- **Starting point:** all six repositories use `feature/ra-622-spike`, created directly from their current main branches. The existing `feature/ra-622` branches retain their implementation and history. Previous work can inform decisions, but wholesale cherry-picking completed feature slices is not part of the spike.
- **One representative type:** register an independent `add-overseas-site` module in the management backend and frontend, displayed as Add ORS. Re-accreditation supplies the existing contrasting type and workflow. A second new type, a subtype framework and a general change-type registry are unnecessary for this proof.
- **One prepared example:** use a single explicit local target with organisation, registration, accreditation, material and year identifiers, a Granted baseline, and a prepared proposed ORS. Read through the existing ReEx development adapter where useful, but do not infer eligibility from every synthetic response. Only the payload fields necessary for identity, presentation and the demonstrated outcome are required. The preparation belongs to local demo configuration; it is not a production accreditation catalogue or a copy of an application.
- **Minimal operator presentation:** add one new landing-page section for the fixed accreditation. Its minimal summary shows Granted status, target identity, baseline/effective approved sites, the Change link when eligible, and its active request with status/case correlation. Change opens the prepared proposal directly with Submit example; no change-type selection is needed. Viewing either page must not seed a re-accreditation application or create a request. A refresh or return reads persisted data. Other granted accreditation pages have no new Change link, and backend start operations must enforce the same fixed-target eligibility. Use existing form protection, auth, templates and navigation conventions; restrict the demo entry to existing local/development configuration.
- **Minimal operator record:** persist a separate change-request identity, change type, target identifiers, the displayed baseline/proposal, submission status, case correlation, terminal outcome and active-request marker. Persist the identity before sending the submission so retrying the same submission can retain it. Use existing MongoDB and version conventions; do not introduce a general event model, revision history or editable draft lifecycle.
- **One active request:** enforce at most one active request for the exact target accreditation using a partial unique MongoDB index or an equivalent atomic constraint. A read-before-create check or hidden Change link alone is insufficient. A second start must resume/report the existing active request rather than create another case. Opening the prepared-proposal page does not reserve the slot; the protected submission operation creates the request. Unconfirmed submission or outcome delivery retains the slot. Confirmed approval, refusal and withdrawal make the request terminal and release it; preserve the request and its case as history.
- **New attempt after closure:** confirmed approval, refusal and withdrawal restore Change. A later explicit submission creates a new request/case identity and reuses the unchanged predefined proposal, even if an earlier request approved the same site details. Each new request has its own stable proposed-site identity, generated once and retained through submission/outcome retries. Old receipts or callbacks must continue to refer only to the old request and must never close the new one. Retain a small list of terminal attempts on the summary without building a history-search interface. Permitting identical site details across distinct requests is an explicit local demo assumption; final production site identity and duplicate-site rules require refinement in the next ticket.
- **Real submission:** submit through the existing authenticated/signed management ingestion boundary with a type-aware payload. Retain the current re-accreditation contract. The spike must expose any hardcoded re-accreditation assumptions that prevent this, and make only the shared transport or ingestion changes required for the demonstrated path. Frontend API stubs and fabricated case receipts must not substitute for this crossing.
- **Minimal management presentation:** list the case in the existing worklist, identify it as Add ORS, and render a small type-specific detail view using the stored type/template version. Display target identifiers, the proposed site, request/case correlation, state and the implemented actions. Add the new Application type option if the worklist requires it for type selection. Existing unrelated filter combinations, evidence views and full application-summary reuse are not new acceptance requirements.
- **Five-state workflow:** declare `submitted`, `assessment-in-progress` and terminal `approved`, `rejected` and `withdrawn` states. Start assessment moves Submitted to Assessment; Approve and Refuse move Assessment to their corresponding terminal states; operator withdrawal moves Submitted to Withdrawn. Use existing Granted, Refused and Withdrawn display conventions. No payment, duly making, SLA or query state is implemented. These are explicit demo simplifications, not a proposed final statutory workflow; keep request status visibly separate from Granted accreditation status.
- **Engine and module ownership:** the backend engine remains authoritative for transitions. Use module-scoped services for behaviour and the existing audit/version/state guards. Decision and withdrawal each have one supported service operation that records the case outcome and performs or tracks its required cross-service effects. An alternative generic action must not bypass that behaviour. Do not build a replacement engine or make one work-item module depend on another; extract shared behaviour only where this path proves a concrete need.
- **Minimal outcome contract:** reuse the existing management-to-operator transport and signing where possible, with a type-aware route/contract owned by the change request. Correlate each decision with the persisted request, case and target. Reject mismatched or conflicting outcomes. Record the terminal outcome durably; replaying the same outcome must be harmless. No re-accreditation application may receive the new type's outcome.
- **Operator withdrawal:** offer Withdraw request only while the management case is Submitted. Resolve its eligibility through the existing status/read transport as needed; the management service enforces the current state even if the operator page is stale. Send withdrawal from the operator backend to the real linked management case using existing service-authentication conventions. Only confirmed closure records Withdrawn and releases the operator's active slot; failed or rejected delivery leaves it active. Refresh must show assessment/terminal state accurately enough to remove the withdrawal action. No queried/assessment withdrawal journey, elaborate reason wizard or full race matrix is required.
- **Approval effect:** reconstruct the fixed accreditation's approved sites from its original unchanged ReEx baseline plus this target's durably approved ORS proposals. Each approved request contributes exactly one entry using its stable proposed-site identity; different approved requests contribute separate entries even when the predefined site details match. Do not deduplicate across requests by site name, country or the shared example identity. Callback replay or repeat delivery for the same request contributes no additional entry. Refused, withdrawn and pending proposals contribute no approved site. Preserve earlier approved additions, Granted status, accreditation identity, baseline sites and unrelated details. Do not create a mutable ReEx replacement, amend a next-year re-accreditation application or add an external registry-write API.
- **Honest delivery state:** make successful versus failed cross-service delivery observable. A failed decision callback must not appear as received on the operator page, and an unconfirmed withdrawal must not appear completed. Reuse existing acknowledgement/retry behaviour where applicable. If it cannot be reused without substantial work, provide the smallest explicit retry of the same recorded operation and document that limitation. No background reconciliation system, general delivery framework or exhaustive failure matrix is required.
- **Persistence and versioning:** management uses existing work-item persistence, audit and template snapshots. Request/case identities, terminal outcomes, prior attempts and the effective approved-site view must be readable after the application services restart with MongoDB retained. Versioning is proved through a focused backend check using two declarations of the same type; a second production workflow, version-switch UI or migration framework is unnecessary.
- **Local runtime:** connect the operator frontend/backend and management frontend/backend using existing configuration mechanisms, distinct frontend session cookie names and correct callback URLs. Prefer ports 3000, 5000, 3001 and 8085 respectively. Use existing stub sign-ins, MongoDB and unchanged ReEx development fixtures. Select separate spike databases so existing RA-622 demo data and receipts are preserved and cannot supply the new demonstration's results. Disable real notifications. Upload/storage infrastructure is unnecessary for prepared field data. Document the minimal launch commands and example identifiers; a reusable orchestration platform is out of scope.
- **Existing access rules:** retain organisation ownership, caseworker/support permissions and protected mutation routes. Do not introduce a new permission scheme. Use existing translation conventions for any added interface text; comprehensive Welsh or accessibility journey expansion is deferred.
- **Approach note:** record the observed changes per service, the recommended separate request and case-type design, a sequence diagram of the demonstrated submission/outcome flow, and any limitations in module isolation, ingestion, presentation or versioning. Compare the approach conceptually with tonnage changes and interim-site additions. Identify proposed ReEx amendment contracts, effective-date/issuing-limit questions, concurrency policy and fee/workflow decisions as unresolved delivery dependencies where they are not established by this proof. Do not claim that the live ReEx interface has been verified.

## Testing Decisions

- **Primary seam:** one connected scenario crosses the four real services through public interfaces. Open the landing-page section and fixed summary, submit the prepared proposal, start assessment and refuse, then submit a new request and withdraw before assessment, then submit a third request and approve. Follow Change again and approve a fourth request containing the same predefined site details without resetting data. Verify distinct request/case/site identities, retained terminal history, restored Change after each outcome, no additions from refusal/withdrawal, and exactly one extra site entry per newly approved request. Compare against the starting approved-site view so earlier demo runs remain valid and preserved. Use the two existing browser-test repositories for their respective portal portions, passing actual request/case identifiers between them. A manual walkthrough uses the same flow. No new test repository or browser framework is needed.
- **Focused API checks:** use existing public backend integration patterns and existing MongoDB test infrastructure to check atomic single-active-request creation, invalid/out-of-order transitions, terminal-state mutation, wrong request/case/target correlation, and harmless duplicate decision/withdrawal delivery. Repeating the same submission retains one request/case/site identity; a new submission after confirmed closure has new identities. Approving two separate requests with identical site details yields two added entries; replaying either approval leaves that count unchanged. An old terminal callback must not alter a subsequent request. Unsupported targets cannot start changes. State/version guards reject withdrawal once assessment starts; comprehensive timing/failure permutations are deferred.
- **Versioning check:** submit under v1, register a changed v2 declaration in the existing backend test setup, and verify that the v1 case retains its stored version and action rules while a newly submitted case uses v2. Exercise public submission/read/action behaviour rather than private engine hooks. Frontend template resolution uses the existing versioned registry; reuse its coverage and add a new-type assertion only if needed.
- **Durability check:** restart the application services once without clearing MongoDB and verify the same request/case/site identities, refused/withdrawn history and all approved additions, with exactly one entry per approved request. Change remains available when there is no active request, so the demonstration can continue on the same data. Unsaved frontend session recovery is not required.
- **Existing behaviour:** run relevant existing checks for any shared submission, worklist, template or transport code changed. Verify the existing re-accreditation type can still be listed/read and its relevant actions are unaffected; do not reproduce its entire journey as a separate prerequisite project.
- **Test quality:** test observable behaviour and genuine boundaries. Avoid tests that mirror declarations, comprehensive product acceptance suites, repeated full-suite runs without a reason, or new test seams below existing public endpoints.
- **Evidence:** the approach note records the exact demo configuration, repository revisions, checks actually performed, limitations and any unresolved failures. Decision callbacks must come from management, and withdrawal must close the actual management case. Directly seeded terminal outcomes do not establish this proof.

## Out of Scope

- A complete Add ORS product journey or production rollout.
- Full ORS/interim-site capture, country/material rules, evidence uploads/scanning/downloads, check-your-answers and declaration.
- Current-accreditation catalogue, Change selection, save-and-return drafting, comprehensive request history and multiple concurrent operator journeys.
- Fees, payment details, payment dates, duly making, SLA calculation/extension and statutory workflow confirmation.
- Query/resubmit, query-origin recovery, withdrawal after assessment starts, additional configurable ORS proposals and production duplicate-site validation. Reusing the predefined proposal in separate requests is included.
- Changes to ReEx fixtures, live ReEx reads/writes, issuing-limit amendments and Public Register changes. Only the local fixed-accreditation approved-site projection is included.
- Tonnage-change or interim-site implementation; only their design implications are recorded.
- A second new case type, cross-type abstraction framework, task checklist framework, broad framework redesign or speculative shared-code extraction.
- Full filter-combination coverage, comprehensive localization/accessibility acceptance, real notifications and production entitlement-policy changes.
- Comprehensive concurrency/recovery hardening, background effect workers and production reconciliation. Atomic single-active-request creation and the narrow correlation, replay and state guarantees specified above remain in scope.
- Generating implementation tasks, implementing the demo or creating external delivery tickets during this specification step.

## Further Notes

### Carrying the spike into feature delivery

After the demo and approach are approved, the spike branch is the foundation for the full feature. Keep the useful transport, independent request identity, active-request constraint, module registration, engine integration, callback code and approval projection. Replace the fixed target/prepared proposal with the real operator journey, and extend the workflow with a new template version. The simplified spike workflow must not silently acquire final-feature rules for already persisted cases.

The approach note must include a follow-on work record titled **Complete Add ORS changes against granted accreditations**. This is a scope record for later ticket refinement, not another executable task list. It should identify what the spike already proves and describe the remaining work:

| Remaining area            | Scope to refine for the next ticket                                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Operator journey          | Real eligible-accreditation entry, request creation/resumption, full ORS validation, evidence and declaration.                                         |
| Assessment and money      | Confirm fees and SLA; implement payment details, duly making, assignment and the intended assessment progression.                                      |
| Outcomes                  | Extend demonstrated approval/refusal to the final payload, authorized external effects, delivery recovery and agreed accreditation amendment/readback. |
| Corrections and closure   | Query, full proposal/evidence correction, submitted revisions, resubmission, withdrawal at additional eligible stages and further distinct additions.  |
| Isolation and reliability | Extend the single-active-request policy to other change types and re-accreditation conflicts; harden concurrent writes, retries and ownership.         |
| External dependencies     | Confirm ReEx amendment support, effective dates, issuing-limit effects, authoritative target data and any required work in other teams.                |
| Delivery acceptance       | Final designs, localization/accessibility, complete journey/regression coverage, operational configuration and rollout requirements.                   |

Where an area still needs product, design or external-team decisions, record those dependencies rather than inventing an answer. If full RA-622 delivery includes tonnage changes or interim sites, record them as separately refined scope; this ORS proof does not deliver those journeys.

### Review

The human review demonstrates refusal, withdrawal, new attempts and final approval through the connected applications, including the entry point and effective approved-site view, and inspects the approach note and follow-on scope. Approval confirms that the technical approach is a suitable basis for delivery; it does not sign off final designs, tariffs, statutory workflow or external registry behaviour.

No existing RA-622 feature commits are included in the spike baseline. Existing local runtime caches are outside the branch's implementation and must not be mistaken for evidence produced by the new demo.
